# Adding a model

The repeatable slice for putting a new table into `apps/api`. Run every command from
`apps/api/`, with the database up (`docker compose up -d` from the repo root).

Two steps fail *silently* if skipped — step 4 (registry) and step 6 (review the
generated SQL). Everything else fails loudly. Spend your attention there.

## 1. Design the model before writing code

Write or update `docs/models/<name>.md`. Copy the shape of
`docs/models/organization.md`: purpose, a field table with the reasoning per field,
a **"deliberately NOT included yet (YAGNI)"** section, and any open questions.

Check `DESIGN.md` — the build order and the §10 open questions live there. If the
model depends on an unresolved question, resolve it with the human first rather than
guessing. Naming a field is cheap; unpicking a wrong relationship after three
migrations is not.

Conventions already decided (don't relitigate): **UUID PKs everywhere**, and
`created_at` + `updated_at` (tz-aware) on **every** table.

## 2. Branch

```bash
git switch -c feat/<name>-model
```

Never commit to `main`.

## 3. Failing test first

`apps/api/tests/test_<feature>.py`. Use the `session` fixture from `conftest.py` — it
wraps each test in a transaction that is rolled back, so tests never see each other's
data.

```python
def test_create_and_read_<thing>(session):
    obj = Thing(name="…")
    session.add(obj)
    session.commit()
    session.refresh(obj)

    fetched = session.get(Thing, obj.id)
    assert fetched is not None
    assert isinstance(fetched.id, uuid.UUID)   # UUID PK auto-generated
    assert fetched.created_at is not None      # timestamps come from the DB
```

Run it. **Watch it fail for the right reason** (model doesn't exist — not a typo in
the import). A test that was never red proves nothing.

## 4. Write the model, then register it

`apps/api/app/<feature>/models.py` — inherit `TimestampMixin` from `app.core.models`
to get both timestamp columns:

```python
class Thing(TimestampMixin, table=True):
    """One-line statement of what this represents in the domain."""

    __tablename__ = "things"          # plural, snake_case

    id: uuid.UUID = Field(default_factory=uuid.uuid4, primary_key=True)
    name: str
    slug: str = Field(unique=True, index=True)
```

**Then import it in `apps/api/app/models.py` and add it to `__all__`.**

This is the silent-failure step. `alembic/env.py` and `tests/conftest.py` both build
their metadata from that registry. A model missing from it is invisible: autogenerate
emits an **empty migration** and reports success. If a migration comes out empty, this
is almost always why.

Now make the test pass, then refactor.

## 5. Generate the migration

```bash
uv run alembic revision --autogenerate -m "create things"
```

`post_write_hooks` in `alembic.ini` run `ruff check --fix` + `ruff format` over the new
file automatically, so it lands already matching repo style.

`alembic/script.py.mako` is customized (modern typing, `import sqlmodel.sql.sqltypes`
rather than `import sqlmodel` — `ty` exits 1 on the latter). **Never re-run
`alembic init`**; it would overwrite that template.

## 6. Read the generated SQL — do not trust it

Autogenerate is a diffing heuristic, not a source of truth. Open the file and check:

- The table and columns are actually there (empty body → you skipped step 4).
- Nullability, uniqueness and indexes match the design doc.
- No unrelated drops. Autogenerate happily writes `drop_table` for anything it can't
  see — a model you forgot to register looks exactly like a table you meant to delete.
- **Column-type changes and renames are usually wrong.** Autogenerate sees a rename as
  drop + add, which silently discards the data. Rewrite those by hand
  (`op.alter_column(..., new_column_name=...)`).
- `downgrade()` genuinely reverses `upgrade()`.

## 7. Verify against a real database

```bash
uv run alembic upgrade head
uv run alembic downgrade base && uv run alembic upgrade head   # round-trip
uv run alembic check                                           # no model/migration drift
```

`alembic check` reporting "No new upgrade operations detected" is the proof the
migration and the models agree. The round-trip is the proof `downgrade()` works —
autogenerated downgrades are rarely exercised until the day you urgently need one.

Inspect the result yourself:

```bash
docker compose exec postgres psql -U casepilot -d casepilot -c '\d things'
```

## 8. Full gate, then ship

```bash
uv run ruff check . && uv run ruff format --check . && uv run ty check && uv run pytest
```

Coverage must not regress. Note `ty` **exits 1 on warnings**, and CI does not yet run
it — the pre-commit hook is the only gate, so don't bypass it with `--no-verify`.

Then: commit in small atomic steps → `gh pr create` → CI green →
`gh pr merge --squash --delete-branch` → update `PROGRESS.md` → **pause**.

## Gotchas worth remembering

- Tests build their schema with `create_all`, **not** migrations. A broken migration
  will not fail the test suite or CI. Step 7 is the only thing standing between you
  and a migration that has never run.
- `sqlalchemy.url` in `alembic.ini` is a dummy placeholder; `env.py` overrides it from
  app settings. Editing the ini value does nothing.
- `updated_at` bumps via SQLAlchemy's `onupdate`, which is Python-side: it fires on ORM
  writes, not on raw `UPDATE` statements or bulk queries.
- Migrations are append-only once merged. Never edit a migration that has run anywhere
  but your laptop — write a new one.
